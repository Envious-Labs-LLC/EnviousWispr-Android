## 3. Design
Use a dedicated Sounds page with two switches, a list/grid of all twelve choices and separate Preview buttons that never select a pair. Copy Mac names/descriptions and derive any displayed waveform from actual samples. Persist selected pair, recording-sounds enabled and recording-vibration enabled in the existing preference authority. Invalid pairing reads Whisper Tick. Both rendered defaults and DataStore defaults must agree. Freeze choices for one take, including its vibration choice.
A narrow on-demand playback owner prepares the selected pair during STARTING, supports start and stop, and returns whether playback actually began. A late preparation callback never replays a missed cue. No cue readiness wait on the heart path. Snapshot the pair for stop only when start began successfully; consume once. Manual, silence and duration-cap stops await a new appended onCaptureClosed event confirming successful resource cleanup, emitted immediately before the unchanged ending event. Existing onEnded cleanup is attempted but not proof of release success. Cancellation after live also awaits confirmed closure; pre-live cancellation has no sound, and processing cancellation never adds a second stop. Explicit interruption handling must consume or invalidate the armed pair once; abrupt process death cannot promise audio output. Repeated/stale callbacks never reopen a pair.
Playback and focus are optional: acquire transient focus with attributes matching the player; refuse delayed focus, skip a denied cue, release on completion/error/loss/teardown. Never change system volume, communication mode, microphone selection or Bluetooth routing. Prefer completion-driven MediaPlayer ownership over an arbitrary timer. Use MediaPlayer prepared asynchronously per selected pair, with completion/error callbacks owning cleanup; any change to capture or route ownership escalates scope before coding.
Preview shares the output owner, replaces prior preview, plays clicked start then stop with Mac gap, and is canceled when leaving the page or admitting a real take. One main-process busy signal owned by real session admission/finish includes STARTING, independent of settings-screen visibility. No polling. No idle player, job, audio focus or collector introduced.

## 3b. Ownership

## 4. Contract deltas
AppPreferencesState and its stored keys gain sound enabled, pairing and recording-vibration enabled. SessionPreferencesSource snapshots/freeze carry them without rereading storage at stop. SessionHost gains narrow playback/busy hooks (proposed). HapticCue result policy is unchanged; recording transition/cancel callers apply the frozen recording switch. Playback success means a stream began, never a promise it was physically audible. A stop requires a successfully begun start. Preview is an explicit temporary action and never changes persistence.

## 5. State and lifecycle audit
Population: session states IDLE, STARTING, RECORDING, PROCESSING, CANCELLING, FINISHING, ERROR; command cases start, toggle, stop, cancel; capture endings manual, silence, max duration, failure, still-running; destruction and disconnect callbacks.
IDLE: no pending cue or focus. STARTING: acquire busy and prepare current pair; no cue until publishLive. RECORDING: start at most once, snapshot only on successful playback. PROCESSING after requested manual stop: retain pending stop until capture closes, then consume once before transcription work. Silence/cap: already-closed callback triggers that same consume. CANCELLING before live: no audio; after live: consume at close; during processing: no repeated stop. ERROR/disconnect: invalidate loading and consume/drop exactly once according to observable capture closure, never pretend it closed. FINISHING/destroy: cancel pending preview/preparation, release non-playing resources; retain only already-playing cue until completion with no Service reference. OS process kill: resources disappear, no promised final cue.
Async classes: Interrupted (focus loss/call destroys playback only); Deleted (page leaving cancels preview); Mutated (settings apply next take); Concurrent (real start replaces preview, command latches unchanged); Absent (missing resource/player/focus skips feedback, take proceeds); Stale (take/generation token prevents late preparation or stop callback affecting next take). Existing stop grace and first/last samples are unchanged.
