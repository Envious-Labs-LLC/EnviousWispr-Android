## 1

The identity-sensitive synchronization is:

- `state`, `arbiter`, `polishLedger`, `polishSubmissionLock`, `publishLock`, `serviceJob/serviceScope`, `draftId`, `teardownStarted`, and `pendingHistoryUpdates` must remain single shared instances (`DictationSessionService.kt:186-242,306-317`). `TakeArbiter` additionally depends on token identity using `===` under its own lock (`TakeArbiter.kt:38-107`). The polish ledger is one atomic first-wins value (`PolishRequestLedger.kt:18-38`).
- `publishLock` joins live publication, stop, both cancel paths, start failure, and destruction (`DictationSessionService.kt:720-778,961-967,1509-1515,1595-1601,1649-1655,1861-1880`).
- `polishSubmissionLock` joins request opening with processing cancellation (`DictationSessionService.kt:1103-1119,1573-1584`).

Load-bearing `@Volatile` examples:

- `arbiter`: main replaces the closed arbiter, while binder callbacks and workers claim it (`194,531-543,1032-1067,1129-1179`).
- `takePeakAmplitude`: `TranscribeThread` writes it and the ASR callback classifies an empty result (`996-999,1032-1085`).
- Preference fields: IO collectors write them; later main/worker activity reads them. The deferreds publish the first snapshot, but later preference emissions still need visibility (`270-317,405-425,564-599,637-639`).
- `targetPinAtStart`, `recordingDurationMs`, `captureDeviceLabel`, and `sessionPreferences`: main or `TranscribeThread` writes, then the IO publication coroutine reads (`255-280,988-1002,1091-1128,1288-1344`).
- Notice latches cross main resets and polling-thread reads (`292-315,633-636,891-933`).

`facts` is only a volatile reference; its mutable members are not independently synchronized (`210,729-739,997-1009,1258-1264`).

Moving these onto one coordinator created in `onCreate` does not itself alter visibility. Splitting, copying, or recreating them would. Existing binder references and bound flags are notably not volatile despite worker reads (`244-249,677,785,874,976-1024`).

## 2

Main-thread assumptions:

- Android lifecycle and `ServiceConnection` callbacks directly mutate session state (`325-433,435-470,1861-1935`).
- Bubble correctness relies on synchronous `onStartCommand` arrival order on main (`474-505`). Calling `handle` directly preserves it. Routing commands through an unconstrained `postToMain` does not guarantee it.
- Live publication explicitly checks main (`722`) and is posted there by `LiveWaiter` (`673-690`). This ordering is preserved only if the seam means FIFO posting to the same main Looper.
- Main coroutine dispatch occurs for settings failure/bind (`571-599`) and toast display (`954-958`). `Main.immediate` may execute inline when already on main; an always-posting seam is not line-for-line equivalent.
- `mainHandler.post` sites are: live publication (`689`), polish notice before persistence (`1282-1288`), fallback toast (`1479-1481`), error toast (`1668`), post-History teardown (`1683-1696`), and destroyed-capture unbind (`1927`). A Handler-backed FIFO seam preserves these. The proposed interface alone does not state FIFO, same-Looper, or inline behavior.

## 4

Fresh-instance reset is essential for `state`, which finishes as `FINISHING` and is never restored to `IDLE`; the next instance supplies `IDLE` (`DictationSessionService.kt:1678-1695`). Destruction also permanently cancels `serviceJob` and closes the detector (`1861-1904`).

Fresh construction additionally clears the arbiter, ledger, atomics, bound references, draft jobs/list, transcript fields, readiness deferreds, and per-take latches (`186-317`). `BluetoothTipGate.PROCESS`, overlay state, paste state, telemetry, bubble ledger, tile state, and notifications remain process/static or externally stored.

A coordinator created once per Service instance preserves this lifetime. It neither preserves session state between takes nor loses the deliberate process-scoped Bluetooth gate.
