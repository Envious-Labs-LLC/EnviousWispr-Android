## B. The seam

Move the ledger, decision and loss latches, warm-up guard, watchdog, request listener and validation, vocabulary restoration, deterministic fallback, and request cancellation. Keep admission, the speech-versus-terminal decision, `publishResult`, History, notice, and insertion in the coordinator.

The controller needs the admitted take ID, frozen preferences at preparation, request-ID clock through the ledger, timeout clock, session scope, IO dispatcher, current polish link supplier, language detector, log, defect reporter, and a narrow owner-supplied “still live” check. No main dispatcher or host clock is used by today’s polish request path. It returns exactly one sealed `Polished(text, engine, reason, status, latency, context)`, `Fallback(text, reason, context)`, or `Lost` result. The coordinator retains raw words for speech failure and the publication payload.

## C. Concurrency

`polishSubmissionLock` currently joins the PROCESSING/arbiter check to ledger opening and the cancel reservation. `PolishDecision` and ledger claims pick the first answer, watchdog or disconnect. `polishLost` latches a pre-answer failure; `polishFailureReported` limits failure reporting to once per take. Main handles disconnect/cancel/destroy, the session scope handles submission/watchdog, and binder callbacks can answer directly on binder threads ([PipelineBindings.kt:157](/Users/m4pro_sv/Developer/EnviousLabs/EnviousWispr-Android/.claude/worktrees/issue-236-warm-up-off-main/app/src/main/java/com/envi/wispr/ui/PipelineBindings.kt:157)). Keep one shared admission/submission lock across the owner’s cancel reservation and the controller’s open/claim/close. Never hold it across a binder call. The coordinator’s arbiter remains the final guard against publication after cancel or destroy.

## D. Recommended design

- Construct one `TakePolishController` after take admission, with the dependencies in B.
- Expose `connected(policy)`, `disconnected()`, `prepare(raw, preferences)`, `forceFallback(reason)`, and idempotent `cancel()`.
- Deliver one sealed prepared-text outcome through a callback; the controller never publishes it.
- Keep the first-loss and first-defect latches for that take’s full lifetime.
- Arm the watchdog before sending the request; cancel the exact ID after a late registration too.
- Let the coordinator handle blank ASR and all terminal claims before calling `prepare`.
- Replace coordinator call sites with controller calls; delete the moved fields and methods in that change.

## F. Risks

1. Splitting the submission lock from cancel can send an uncancellable request.
2. A late binder answer can rewrite facts before the terminal arbiter rejects publication.
3. Reconnect can accidentally clear a take’s loss latch.
4. Moving warm-up can put a synchronous binder call back on main.
5. Fallback must preserve restored, cleaned words and the failure notice.

## Coverage round

FINDINGS

1. **Keep the raw transcript with the session owner.** The draft moves it into the controller (§3, lines 77 and 86), but speech failure reads it at `DictationSessionCoordinator.kt:514` and final publication uses it at `:1235-1237`. It is currently recorded before the polish coroutine starts (`:1007`). **Drop-in plan text:** “The coordinator retains `rawTranscript`. Record it under the shared lock immediately when speech answers, before the blank-text decision or any launch. Pass the text to `prepare`; use the coordinator’s copy for speech failure and publication.”

2. **Make the speech-loss answer unambiguous.** `speechLost(): Boolean` (§3, line 73) cannot safely mean both “no transcript” and “polish already won.” Today, a nonblank transcript with a claimed polish answer does nothing; only an absent transcript may commit `ASR_PROCESS_DIED` (`DictationSessionCoordinator.kt:515-525`). **Drop-in plan text:** “The coordinator checks whether its raw transcript is blank. For nonblank text, ask the controller to claim a `SERVICE_DIED` fallback; a lost claim does nothing. Only the blank branch may commit the speech failure.”

3. **Do not call the polish binder inside the shared lock.** The proposed one-for-one `cancelOpen()` replacement (§3, lines 81 and 84) would retain the current nested call at `DictationSessionCoordinator.kt:1375-1384`; `cancelOpenPolishRequest` calls `pipeline.polish?.cancel` at `:1194-1197`. That contradicts the draft’s lock rule and can stall main. **Drop-in plan text:** “Under the shared lock, reserve cancellation, set CANCELLING, record whether a request was open, and close its ledger entry. Release the lock before sending binder cancel. Apply the same claim-then-send order to `speechLost` and disconnect. Keep the submitter’s post-registration re-send using its captured link (`:1145-1149`).”

4. **Publish a complete take/controller pair and guard late outcomes.** The draft publishes `polish` before `take` (§3, line 80), although `TakeContext.NONE` deliberately has a closed arbiter (`TakeContext.kt:24-33`). It also says the old arbiter guards late callbacks, while `publishResult` reads the *current* take and writes its facts before reserving (`DictationSessionCoordinator.kt:1224-1252`). **Drop-in plan text:** “Build both locally, then publish `take` before the controller in the uninterrupted admission call; use a nullable controller before admission, including idle destroy. Bind only after both exist. Capture the admitted take ID in `onPrepared`; reject a mismatched ID before calling `publishResult` or writing facts.”

5. **Do not share an open-request ledger across controllers.** The draft calls it “shared across takes” (§3, line 56), but `PolishRequestLedger.open()` replaces the open ID and `close()` closes whichever ID is current (`PolishRequestLedger.kt:20-38`). A late old-controller close could therefore close a newer request if a coordinator ever admits another take. **Drop-in plan text:** “Give each controller its own ledger. Share only the request-ID source for unique IDs. Update the rig’s injection to a ledger factory; do not rely on a shared ledger to reject old callbacks.”

6. **Make §11 prove the new seams.** Existing tests cover the user outcome, but §11 lacks a controlled race between cancel and request registration, a prior-controller callback after new admission, and null, mismatched and legacy callback shapes (`DictationSessionCoordinator.kt:1081-1132`). The proposed re-send mutation is real only if the fake holds registration until after cancellation (`DictationSessionRig.kt:597-603`). **Drop-in plan text:** “Use bounded gates to hold request registration, cancel, then release it and verify the captured link receives the second cancel. Test a stale controller outcome against a newer take and every invalid callback shape. Run each stated mutation and record the test that turns red.”

## Grounded round 1

FINDINGS

1. **The re-send rule is still too narrow.** The draft preserves a post-registration re-send, but §11d tests only cancellation. Today the submitter checks `polishLedger.openId != requestId` after the request call on **every** path, including a callback or watchdog that already claimed it (`DictationSessionCoordinator.kt:1145-1149`). **Drop-in plan text:** “After `polishRequestForTake` returns or throws, compare this controller’s ledger `openId` with the request ID. If different, send cancel on the link captured for that request. This is a read, not another claim. Test cancellation and an answer that arrives before the request call returns.”

2. **Keep binder-thread fallback outside the lock.** `publishFallback` can run directly from a binder callback (`DictationSessionCoordinator.kt:1081-1106,1158-1168`; `PipelineBindings.kt:194-197`). The draft says where `sendCancel` runs, but does not say where `onPrepared` runs. **Drop-in plan text:** “Claim or close under the shared lock; release it before `sendCancel`, deterministic cleanup, defect reporting, or `onPrepared`. `cancelOpen()` must not be called while its caller holds the lock. Test the lock state during both binder cancel and prepared-text delivery.” Remove §3’s claim that `oneway` makes this “not a latency change”; it does not establish that.

3. **Warm-up must capture the connected link.** The constructor comment says the link is read at each use (§3, line 59). Today `onPolishConnected` captures the link and policy on main, then uses that same link on IO (`DictationSessionCoordinator.kt:542-552`). **Drop-in plan text:** “In `connected(policy)`, capture the current `PolishLink` before launching IO. Check that this take is still live immediately before sending, then warm that captured link. Later request and cancel paths may read the current link as specified.”

4. **The proposed previous-take coordinator test cannot run through today’s lifecycle.** `finishSession` leaves this owner FINISHING and stops its Service; the next take gets a fresh owner (`DictationSessionCoordinator.kt:59-62,1463-1483`). §11g cannot admit a second take through the same coordinator, so dropping the take-ID check would not necessarily turn it red. **Drop-in plan text:** “Test two controller instances against a controlled owner callback seam, or explicitly construct a stale `onPrepared` callback after replacing the test owner’s take context. Prove the stale callback writes no facts and leaves the current request open. Do not describe this as a normal two-take coordinator flow.” Also correct §7-9: `publishResult` writes facts **before** arbiter reservation (`:1224-1252`).

5. **“Exactly one” overstates the outcome contract.** §2.1 line 35 promises one `PreparedText` per take, while blank speech ends before polish (`DictationSessionCoordinator.kt:1006-1016`), and cancellation can close an unanswered request (`:1374-1384`). **Drop-in plan text:** “Emit at most one `PreparedText` for an admitted nonblank speech answer. Emit none when the owner ends the take first. A loss before speech is latched and becomes a fallback only if nonblank speech arrives.”
