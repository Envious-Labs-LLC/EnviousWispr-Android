ASR release-order review — DONE

TL;DR: the recognizer ownership logic is concurrency-safe, but the immediate process-kill premise is not. Android can start a replacement service record while the old one is still being destroyed. The current test plan also contains one baseline-impossible row and one mutation, R3, that stays green.

## 1. FOUND

**P1: A replacement `AsrService` and client can overlap the old service’s destruction. Killing `:asr` can therefore kill newer work.**

Evidence:

- Android runs lifecycle callbacks on the process main thread, but Binder methods run concurrently on Binder-pool threads. Main-thread serialization does not prove that no new binding or replacement service record exists. [Android’s Service documentation](https://developer.android.com/reference/android/app/Service) and [process/thread documentation](https://developer.android.com/guide/components/processes-and-threads) state these separate threading rules.
- AOSP removes the old service record before scheduling its destruction at `ActiveServices.java:4690`, then schedules `onDestroy` at `:4771`. AOSP explicitly handles “another instance of it being started in parallel” at `:1350`. [AOSP ActiveServices](https://android.googlesource.com/platform/frameworks/base/+/a6f9b086eb53/services/core/java/com/android/server/am/ActiveServices.java#4690)
- The plan claims no newer generation can exist at [issue-212 plan:59](/Users/m4pro_sv/Developer/EnviousLabs/EnviousWispr-Android/.claude/worktrees/issue-212-asr-release-order/docs/feature-requests/issue-212-2026-09-22-asr-release-order.md:59) and [issue-212 plan:157](/Users/m4pro_sv/Developer/EnviousLabs/EnviousWispr-Android/.claude/worktrees/issue-212-asr-release-order/docs/feature-requests/issue-212-2026-09-22-asr-release-order.md:157). That premise is too strong.
- A new session can bind immediately through [PipelineBindings.kt:98](/Users/m4pro_sv/Developer/EnviousLabs/EnviousWispr-Android/.claude/worktrees/issue-212-asr-release-order/app/src/main/java/com/envi/wispr/ui/PipelineBindings.kt:98), after the prior session unbinds at [DictationSessionCoordinator.kt:1662](/Users/m4pro_sv/Developer/EnviousLabs/EnviousWispr-Android/.claude/worktrees/issue-212-asr-release-order/app/src/main/java/com/envi/wispr/ui/DictationSessionCoordinator.kt:1662).
- Killing that replacement causes `onSpeechDisconnected`; during processing this fails the take at [DictationSessionCoordinator.kt:470](/Users/m4pro_sv/Developer/EnviousLabs/EnviousWispr-Android/.claude/worktrees/issue-212-asr-release-order/app/src/main/java/com/envi/wispr/ui/DictationSessionCoordinator.kt:470).
- No other service shares `:asr`. The manifest assigns only `AsrService` there at [AndroidManifest.xml:98](/Users/m4pro_sv/Developer/EnviousLabs/EnviousWispr-Android/.claude/worktrees/issue-212-asr-release-order/app/src/main/AndroidManifest.xml:98). The harm is to a replacement ASR generation, its binding, and process-wide application state, not another service.

Exact replacement for section 3.1:

> ### 3.1 Teardown never kills the process  
> `onDestroy` closes admission, masks readiness, queues recognizer release on the single worker behind work that already passed admission, calls `worker.shutdown()`, and returns without waiting. It never calls `Process.killProcess`. If a native call is still running, the worker retains the old recognizer until that call returns, then releases it. Android may create a replacement service record while the old record is still being destroyed, so process termination cannot be proven safe for a newer binding or service generation. A permanently wedged native call may retain the old owner until Android ends the process; solving that requires a separately designed process-generation protocol and is outside this change.

Corresponding code change: remove `busy` and `endProcess`; always use the queued-release branch currently at plan lines 118 to 128.

The owner marks the entire task busy at [issue-212 plan:137](/Users/m4pro_sv/Developer/EnviousLabs/EnviousWispr-Android/.claude/worktrees/issue-212-asr-release-order/docs/feature-requests/issue-212-2026-09-22-asr-release-order.md:137). Thus the process can be killed while reading a file or delivering a result, with no native recognizer call active.

Exact replacement if the kill design were retained:

> `busy` means any admitted owner task is running, including file preparation and callback delivery; it does not prove that a native recognizer call is currently executing.

That replacement exposes why the safer section 3.1 replacement should remove process killing.
