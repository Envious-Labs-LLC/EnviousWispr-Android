## D3. Stability and recomposition

**CLEAN.** This is a known Compose concern and the plan uses the known fix. Compose treats function types as stable, and an immutable holder whose public properties are `val` lambdas or other immutable holders can be inferred stable. Kotlin 2.0.21 is used here (`build.gradle.kts:5-6`), where strong skipping is enabled by default. Strong skipping compares unstable parameters by instance identity and automatically remembers composable lambdas. [Compose lifecycle](https://developer.android.com/develop/ui/compose/lifecycle), [strong skipping](https://developer.android.com/develop/ui/compose/performance/stability/strongskipping).

`remember(viewModel)` is correct. The ViewModel is activity-owned (`SettingsActivity.kt:27-36`); within one composition it keeps the holder identity fixed. After configuration recreation, the new composition executes the initializer again, so the four lambdas at `SettingsActivity.kt:65-76` capture the new Activity even though the ViewModel survives.

`@Immutable` or `@Stable` is unnecessary. These annotations assert a contract rather than creating stability and can break recomposition when used incorrectly. [Official stability guidance](https://developer.android.com/develop/ui/compose/performance/stability/fix). If inference were wrong, the likely user effect would be avoidable recomposition and occasional frame cost, not stale state or misrouted actions; the remembered holder and its callback identities remain unchanged.
