## D4. Main-thread contract

**Finding:** The plan still says destroyed-capture unbinding is one of the six main-Handler posts (`docs/feature-requests/issue-186-2026-09-20-session-coordinator.md:303-305`), but the cleanup may capture only the pipeline and immutable data (`:350-358`). Nothing currently specifies how `pipeline.unbind()` gets back onto that same Handler. Calling it directly from `DestroyedSessionCleanup` would change the thread used at `app/src/main/java/com/envi/wispr/ui/DictationSessionService.kt:1921-1928`.

Add to `PipelineController`:

```kotlin
fun postUnbindToMain()
```

Add verbatim:

> `PipelineBindings` is constructed with `applicationContext` and the Service’s existing `mainHandler`. `postUnbindToMain()` is exactly `mainHandler.post { unbind() }`. `DestroyedSessionCleanup` calls that method after capture cleanup. Normal `finishSession` calls synchronous `unbind()` because it already runs inside the existing main-thread post. Thus both paths retain their current thread and ordering without capturing the destroyed Service or `SessionHost`.
